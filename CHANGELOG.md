## Unreleased

### Features
- A new exception log replaces the one of StackExchange.Exceptional, which stored one row per error. It groups the errors of an application into *issues* by their exception type and the method they come from (the first frame of the application's own code, by `InAppPrefixes`), and keeps for each issue a status (unresolved, resolved or ignored), the first and last seen times and releases, hourly counters for its charts, and its latest events with their request, user and server details. `services.AddExceptionLogger()` registers it and `app.UseExceptionLogger()` adds its middleware and its `ILogger` provider, which put the events in an in-memory queue that a background writer stores in batches, retrying while the store is not available, and an issue that was resolved and fails again comes back as *regressed* (StartSharp).
- The exception log keeps its database small: the stack trace is stored once per issue, only the latest `MaxEventsPerIssue` (20) events of an issue are kept while all are counted, repeats of the same user and address within `RollupSeconds` (60) become one event with a count, and the events and counters older than `RetentionDays` (90) are removed every 6 hours. The values of form fields, query strings, headers and cookies whose names match `MaskPattern`, e.g. passwords, tokens and the authentication cookie, are replaced with `[Filtered]` before an event leaves the request, and the exceptions of requests that the client aborted are not logged (`IgnoreAbortedRequests`) (StartSharp).
- The exception log has its own tables, `exc_Issues`, `exc_Events`, `exc_Counters` and `exc_Rules`, which the migrations of Pro.Extensions create under the new `ProExceptionLog` connection key, which falls back to `ProExtensions`, `ProFeatures` and `Default`, so the log can live in a database of its own, e.g. a central one with another backup schedule; `ExceptionLog:ConnectionKey` in the settings chooses another key. The `ExceptionLog` settings also have `ApplicationName`, `Environment` and `Release` (from the host and the informational version of the entry assembly by default), which are stored with each event, and `ShowAllApplications`, which lists the issues of every application that shares the database, with a filter for them, instead of the current one only (StartSharp).
- How much of an exception is stored is chosen by a *detail level*: `Full`, `Light` (events without their request details), `CountOnly` (only the counters) or `Discard`. Rules give it to the exceptions that match all their conditions, an exception type (full or short name, `*` for any text), a text the message contains, the path of the request and its status code, and can also ignore their issues (`IgnoreIssues`), so a new issue starts as ignored and a resolved one that comes back stays ignored. Rules come from the `ExceptionLog:Rules` settings and from the exception log page, which stores them in `exc_Rules` with their match count and last match; the built-in rules (`UseDefaultRules`) only count antiforgery and bad request errors. A choice made for an issue on the page comes first, then the rules of the page, then the ones of the settings (StartSharp).
- The exception log page of StartSharp lists the issues of the last 24 hours, 7 or 14 days with key figures, a daily chart per issue, search, and filters by status, exception type, environment and application, resolves, ignores (forever, for a time or for a number of events, optionally with a detail level) and deletes them one by one or together, refreshes itself in live mode, tells when there are more issues than the `MaxListedIssues` (2000) most recently seen ones that it reads, as its lists and counts are about those, and lists the rules: the ones of the page, which it adds and edits in a dialog that tells how many stored issues a rule matches and can ignore the unresolved ones among them, the issues with a choice of their own, and the ones of the settings. The page of an issue shows its charts, breakdowns by environment, release, machine and user, and its events one by one with their stack trace, folded to the application's own frames, request, user and server details, and can start a rule for similar exceptions (StartSharp).
- Each logged event has a reference, a key of 32 characters that is not sequential (`ExceptionLogWriter.GetEventKey(exception)`), which the error page of StartSharp shows with a link to the event for users who can see the exception log; `Administration/ExceptionLog#event/<key>` opens the issue at that event, or at its issue when the event itself was not stored (StartSharp).
- `Administration/ExceptionLog/Plain` (`ExceptionLogPlainPage`) shows the exception log as a plain, read-only HTML page without the layout, scripts and styles of the application, for when those are what fails, and lists the events that wait in memory with the error of the store when the database is not available (StartSharp).
- The public demo shows made-up sample issues (`services.AddExceptionLogSampleData()`) instead of the exception log of its server, which visitors can resolve, ignore and add rules to, and which starts over after 30 minutes; the sample store is only in builds with `IsPublicDemo` or `DEBUG`, not in the packages (StartSharp).
- `AddExceptionLogger(connectionString)`, `ExceptionLog` and `SqlErrorStore` of the Exceptional based log are obsolete and still work for applications that have not applied the template changes, which keep logging to the `Exceptions` table; they and the StackExchange.Exceptional package will be removed in a later version (StartSharp). The new log does not read the `Exceptions` table, which can be dropped once its errors are no longer needed.
- Texts of the pages of feature assemblies have their own root, `Pages.`, which `LocalTextPackages.DefaultSitePackageIncludes` sends to the client in the `Site` package and `LocalText.IsLocalTextKeyCandidate` counts as a UI key, like `Forms.` or `Controls.`. **[Breaking Change]** The texts of the Languages and Translations pages moved from `Site.Languages.` and `Site.Translations.` to `Pages.Pro.Languages.` and `Pages.Pro.Translations.`, so translations saved for the old keys need the new ones; the new Exception Log, Roles and User Management pages use `Pages.Pro.ExceptionLog.`, `Pages.Pro.Roles.` and `Pages.Pro.UserManagement.`, and `Site.` is left for the texts of the application (StartSharp).
- The Roles page of StartSharp lists the roles with their member counts on the left, and shows the permissions and the members of the selected one on the right, instead of a grid and a dialog (`RolesPage` of Pro.Extensions). The permissions are a tree of the groups of their keys with a search, a checkbox for each group, counts, and a note for the ones that another granted permission implies, and the changes collect until they are saved or discarded, with a question before they are lost. A role can be compared with another one, showing the differences or only them, cloned with its permissions, get the permissions of another role added or in place of its own, renamed, and deleted, and its members can be searched, added and removed. The role is kept in the hash, e.g. `#role/3`. The template adds `MemberCount` to `RoleRow` and the `ListMembers`, `AddMembers` and `RemoveMembers` actions to the `UserRole` endpoint, and removes `RoleGrid`, `RoleDialog`, `RoleForm`, `RoleColumns` and `RolePermissionDialog` (StartSharp).
- Administrators can grant only what the `PermissionGrants` settings let them (`PermissionGrantOptions`), a list of permission key patterns (`*` for any text) for each tier, `Grantable` (by anyone who manages permissions), `HolderOnly` (only by who has it) and `SuperAdminOnly`, e.g. `{ "Grantable": "*", "HolderOnly": "Administration:*", "SuperAdminOnly": "Administration:Security, Administration:Credentials" }`, separated like `SuperAdmins`. A key gets the most restrictive tier that matches it, one that matches none is `HolderOnly`, a permission is checked with the ones it implies, and a super admin can grant anything; without the section everything is grantable, as before. `services.AddPermissionGrants()` registers the `IPermissionGrantValidator`, which also tells whether an administrator can change the account of a user, e.g. its password: only if the administrator could grant all the permissions of the user, which the application gives with an `IUserGrantedPermissionsProvider`, and only a super admin for a super admin. Its `ValidateListed` lets only the keys that the `IPermissionKeyLister` lists be added, also by a super admin, so a private permission like `ImpersonateAs`, a marker like `*`, a typo, or a role key like `Role:Administrators`, which would give what a role has without being a member, can't be stored, while a key that is no longer listed can still be removed. `BasePermissionKeyLister.IsPrivatePermission` hides the keys starting with `ImpersonateAs`, as the permission service treats them, where `GetPrivatePermissions` hid only `ImpersonateAs` itself. The `Extensions/PermissionGrant/List` service tells a page which permissions the current user can't grant, and the Roles and User Management pages show them read-only, with the roles that have them, and the accounts the user can't change.
- StartSharp checks the permission grants wherever permissions are given or taken: the permissions of roles and users, the members of roles, the roles of a user, and deleting a role. The new `Administration:Credentials` permission is needed to change the password, username or email of another user, or reset the two-factor authentication, and those, the status and deleting a user also need that the administrator could grant all the permissions of the user. The template sets `Administration:*` to `HolderOnly` and `Administration:Security` and `Administration:Credentials` to `SuperAdminOnly`, so a security admin can't make other security admins, nor take over the account of someone with more rights. **[Breaking Change]** Security admins who set passwords need the credentials permission, which only a super admin can grant (StartSharp).
- The two-factor endpoint (`TwoFactorEndpointBase`) has `UserStatus` and `ResetUser` actions for administrators, which an application's endpoint gets without changes: the first tells whether a user has two-factor authentication on, with which methods, their targets masked (e.g. "a•••@example.com", see `TwoFactorTargetMask`) and the preferred one, and the second removes the methods, their targets and the authenticator secret of a user who lost the device, so the user signs in with the password and can set it up again. The first needs `TwoFactorSettings.ViewPermission` (`Administration:Security` by default), the second `ResetPermission` (`Administration:Credentials` by default) and, with an `IPermissionGrantValidator`, that the administrator could grant all the permissions of the user. The User Management page shows them on a Security tab, with the password actions, which moved there from the menu of the user, and says that the password of a user from another source, e.g. LDAP, is managed there (StartSharp).
- The upload editors have no toolbar by default: while they have no file, they show a box that says "Drop a file here or click to choose" ("Drop files here" for the multiple ones), which opens the file chooser when clicked and is highlighted while files are dragged over the editor, like the import of the Translations page. A single file or image editor with a file has a menu on the corner of the file to replace or remove it, a Bootstrap dropdown like the field selection of the quick search, and a multiple one a tile after its files that adds more. The files take the space of the toolbar: their thumbnails are 160 x 120 instead of 128 x 96, and fill their tile, as a stored thumbnail may be smaller or of another shape; the template makes the thumbnails of temporary uploads in that size (`FilePage`, StartSharp and Serene). The `dropHint` and `dropHintDetail` options (`DropHint` and `DropHintDetail` of the upload editor attributes) change the text of the box and add a line under it, as texts or local text keys. The toolbar with the select file and delete buttons comes back with the `toolbar` option (`Toolbar` of the attributes), for all the editors with `FileUploadEditor.defaults.toolbar` and `MultipleFileUploadEditor.defaults.toolbar`, or by overriding `useToolbar`, and it is kept for an editor whose `getToolButtons` adds buttons of its own; then its delete button is hidden while there is no file, instead of disabled. The toolbar is still created and hidden otherwise, as it holds the file input (`FileUploadTexts.DropFileHint`, `DropFilesHint`, `FileMenuHint`, `ReplaceButton` and `AddMoreButton`).
- Sensitive actions ask the user to confirm the password, as GitHub does: a service that calls `IElevationHandler.ValidateElevationToken` fails with the `RequiresElevation` code (`DefaultElevationHandler.RequiresElevationCode`, now also for an expired or invalid token, which had no code), and the page shows a dialog that asks for the password, confirms it with `Account/Elevate`, and calls the service again, after which such actions are allowed for 15 minutes (`ElevationDialog.tsx` of Pro.Extensions, which `initProTheme` sets up with `initElevationRecovery`). It works with `addServiceErrorRecovery` of corelib, which lets a function fix the error of a service call made with `fetch`, e.g. by asking the user something, after which the call is made again once; when the user gives up, the call fails without showing the error. `IPermissionGrantValidator.ValidateGrants` asks for it when one of the permissions is sensitive (`IsSensitive`, one that is not `Grantable`, by itself or by one that it implies), also for a super admin, after telling the ones that can't be granted, and `ResetUser` of the two-factor endpoint asks for it. StartSharp asks for it to change a password, username or email, also of the own account, and to delete a user (`UserSaveHandler` and `UserDeleteHandler` take an `IElevationHandler`).
- A user who must still set up the account is kept to the page that does it until it is done, by `AccountSetupFilter` (`services.AddAccountSetup()`) and the `IAccountSetupRequirement`s: a page redirects there, and a service fails with the `AccountSetupRequired` code, whose arguments are the path of that page, which Pro.Extensions handles by going there (`initAccountSetupRecovery`). The actions with `[AllowDuringAccountSetup]` are allowed, e.g. the password pages, the two-factor settings and the confirmation of the password. It is checked on each request, so a requirement applies at once. `PasswordChangeRequirement` requires a password change of a user whose definition says so (`IHasPasswordChangeRequired`), e.g. after an administrator set the password, which changing or resetting the password ends (`IPasswordChangeRequiredRow`). StartSharp adds a `PasswordChangeRequired` column to `Users` (migration `20261127_1857`), which the set password dialog and the dialog that adds a user ask for, with a checkbox that is checked by default, and the security tab changes with a switch.
- Two-factor authentication can be required: of a user, by a switch of the security tab of the user management page (`2FA/SetRequired`, `TwoFactorSettings.RequirePermission`), or by the settings, for everyone (`RequiredForAll`), the members of some roles (`RequiredForRoles`) or the holders of some permissions (`RequiredForPermissions`). A user who must have it and doesn't sets it up before using the application (`TwoFactorSetupRequirement`), only for the sign-ins that ask for it (`RequiredAuthTypes`, `"Password"` by default). `ITwoFactorManager` has `GetRequiredBy` and `IsSetupRequired`, and the security tab tells what requires it. An application can refuse the changes of `SetRequired` and `ResetUser` for some users with `TwoFactorEndpointBase.ValidateUserChange`, as the public demo does for the admin user.
- Administrators invite users by email instead of creating their accounts (common-features: `IInvitationManager`, `IInvitationPolicy`; Pro: `AddInvitations()`, the `acc_Invitations` table under the `ProAccount` connection key, `SqlInvitationStore`, `InvitationEndpoint`, `InvitationGrid`, `openInviteDialog`): the invitation has the email address, the name and the roles, and its link, whose token is stored only hashed, works once, until it expires (`Invitations:ExpirationDays`, 7), or is sent again or revoked. The user signs up on the sign-up page of the application with a password or an external login of the same verified address, which proves it, so the account is active at once and signed in, with the roles that the inviter can still give (`InvitationAcceptance`). Who can invite whom, with which roles, is decided by the `IInvitationPolicy`s: a denial of any wins, else one must allow it; the default one lets the holders of `Invitations:Permission` (`Administration:Invite`) invite with the roles whose permissions they could grant (`IRoleGrantedPermissionsProvider`, which the application implements), and a role with a sensitive permission needs the password confirmed. The user management page has an *Invite* button and an *Invitations* view, which lists them by state and sends them again or revokes them, and the activity shows `InvitationSent`, `InvitationAccepted` and `InvitationRevoked`. The *Add user* dialog no longer emails a link to set the password, which an invitation does.
- `MembershipSettings.SignUp` (`Membership:SignUp`) tells who can sign up: anyone (`Open`, the default), only the invited ones (`InvitationOnly`), or nobody (`Closed`); the sign-up page of StartSharp, also for the external logins, and the link of the sign-in page follow it.
- The text that `BaseUserListService` searches is in the email addresses too, normalized when the row has `INormalizedEmailRow`.
- An external login that began on the sign-up page, e.g. of an invitation, returns to it with its query (`OpenIdClientControllerBase.SignUpUrl`).
- A user without a password, e.g. one who signs in with an external provider, is asked to set one when an action needs the password confirmed, as the error of the service tells (`DefaultElevationHandler.NoPasswordArgument`), instead of being asked for a password that the user does not have.
- The sign-ins are account events too: `SignedIn`, `SignInFailed` (with `AccountEvent.Reason`, see `SignInFailureReasons`), `SignedOut`, `Elevated`, `ElevationFailed` and `PasswordResetRequested`, which the sign-in page, the external logins, the password grant of the token endpoint, the sign-out, the password confirmation and the forgot password page publish (`PublishSignIn`, `PublishSignInFailed`, `PublishSignOut` of `SignInEventExtensions`). A failed sign-in with a username that no user has is published without it, as it may be a password typed in the wrong box. The emails are still only for the changes of the accounts (`AccountEventEmailHandler.IsEmailed`).
- An administrator signs in as another user in the same browser, and returns with a banner of the pages, instead of a link that opened a new tab (Pro: `AddImpersonation()`, `ImpersonationPageBase` with the `CanImpersonate`, `Impersonate` and `EndImpersonation` actions, `initImpersonationBanner`). The identity of the impersonated user has the impersonator as its actor (`ClaimsIdentity.Actor`), which a return resumes the session of. Who can impersonate whom is decided by the `IImpersonationPolicy`s (common-features): a denial of any wins, else one must allow it; the default one denies the super admins as targets, and lets the holders of `Impersonation:Permission` (`Administration:Impersonate`, a super admin only permission in StartSharp) impersonate the users whose permissions they could grant, and an application adds its own, e.g. a teacher for the own students. `Impersonation:Enabled` turns it off, which returns the ones who impersonate at their next request, and `Impersonation:TimeLimitMinutes` (60) ends it. The impersonator confirms the own password first, and the actions on the security of the account (`[NotDuringImpersonation]`, e.g. the password, the two-factor authentication, the external logins and the sessions) and the password confirmations are refused while impersonating. The impersonation has a session of its own (`AccountSession.ImpersonatorUserId`), which ends with the one of the impersonator, and the activity shows when it started and ended (`ImpersonationStarted`, `ImpersonationEnded`). **[Breaking Change]** `ImpersonateAs`, `UserRow.ImpersonationToken` and `UserHelper.GetImpersonationToken` of StartSharp are removed.
- The audit fields (`InsertUserId`, `UpdateUserId`), the capture log, the data audit log and the account events record the impersonator for an impersonated user (`ClaimsPrincipal.GetAuditIdentifier()`), while the permissions are the ones of the impersonated user; the exception log keeps the impersonated user, with the impersonator in the server details of the event.
- The sign-in cookies are tied to sessions (`AddAccountSessions()`, Pro: `AddAccountSessionStore()` with the `acc_Sessions` table, `SqlAccountSessionStore`, under the `ProAccountSessions` connection key): a sign-in starts a session whose ID the cookie has as a claim, the session is checked at most every `AccountSessions:ValidationMinutes` (1) and a cookie of a session that ended, or of a user who is no longer active, is signed out, and a sign-out ends it (`AccountSessionCookieValidator`, called from the events of the default cookie scheme by `AccountSessionCookieSetup`, so no sign-in code changes; a cookie of before the sessions gets one). The users see and sign out their sessions on the my account page, and the administrators sign a user out everywhere on the security tab of the user management page, after confirming the password (`Serenity.Pro.AccountSession/MyList`, `MyEnd`, `MyEndOthers`, `UserList`, `UserEndAll`, `AccountSessionList`). A password change ends the other sessions of the user, or all of them when an administrator or a reset link sets it, and so does a reset of the two-factor authentication (`AccountSessionEventHandler`); `AccountSessions:Concurrent` = `SignOutOthers` lets a user have one session only. Ending the sessions for security revokes the tokens and the authorizations of the OpenID server of the user too (`IAccountTokenRevoker`, `OpenIdTokenRevoker`), and the activity shows it (`AccountEventKind.SessionsRevoked`) (Pro).
- The account tables fall back to the `ProAccount` connection key, which falls back to `ProExtensions`, so all of them can be moved to another database with one connection, or the logs (`ProAccountLogs`) and the sessions (`ProAccountSessions`) each with one of their own (Pro).
- The account event log stores the account events in the `acc_Events` table (`AddAccountEventLog()`, `AccountEventLogHandler`, `AccountEventRow`), with the user IDs of the type of the users of the application (`UserEntityOptions`), for 90 days unless `AccountEventLog:RetentionDays` says otherwise, under its own connection key, `ProAccountLogs`, which falls back to the default one. `Serenity.Pro.AccountEvent/List` lists the events of all the users for `AccountEventLog:ViewPermission` (`Administration:Security`), and `MyList` the own events of the signed-in user (Pro).
- The permissions tab of a user shows a three-state control for each permission (`PermissionTreeState.triState`): left to the roles, with a tick without a box in blue when a role gives it and in teal when another permission implies it, granted to the user (a green box), or revoked for the user (a red box), and a click goes to the next, so a permission that a role gives can be granted to the user too, e.g. to keep it when the role changes; a legend tells what they mean (Pro).

- The password grant of the token endpoint refuses a user who has two-factor authentication (`TwoFactorPasswordGrantPolicy`), or who must set something up before using the application, e.g. change the password or set up two-factor authentication (`AccountSetupPasswordGrantPolicy`), as it can't ask for the code nor send the user to the page, so the password alone would be enough. `OpenIdAuthorizationControllerBase.GetPasswordGrantDenial` asks the `IPasswordSignInPolicy`s, then the `IPasswordGrantPolicy`s (`GetPasswordGrantDenial`), and the message is the `error_description` of the `invalid_grant` error. Such a user signs in with the browser, e.g. with the authorization code flow (Pro, OpenIddict). **[Breaking Change]** A user who has two-factor authentication gets no token with the password.
- A user who signed up with an external provider, e.g. Google, and is linked to it, can't sign in with a password of the application, e.g. one set later to confirm a sensitive action, unless `OpenIdSettings.PasswordSignInForExternalLogins` allows it (`Deny` by default, `WithTwoFactor` for a user who has two-factor authentication of the application, which the sign-in then asks for, or `Allow`; `ITwoFactorStatus` tells whether a user has it), as the password would get around the sign-in of the provider, e.g. its multi-factor authentication, and keep working for a user who is disabled there. - The users are emailed when their account changes, so they learn of a change they did not make: the password (changed by the user, an administrator, or a reset link), the email address (the email goes to the old one), the username, and the two-factor authentication methods that are set up or removed, or reset by an administrator. - Deleting a role failed when it had permissions or members, as their foreign keys stopped the delete; the delete handler of the template removes them with the role now (StartSharp).
- The super admins, who have every permission and are the only ones who can impersonate other users, come from the new `PermissionService:SuperAdmins` setting (`PermissionServiceOptions`, a list like `"admin, ops"`, separated by commas, semicolons or white space, as a text replaces a setting as a whole where the items of an array would be merged by their index; `"admin"` by default, compared ignoring case, an empty text for none) instead of a check for the `admin` username in the permission service of the templates. `BasePermissionService` takes the options as a new optional constructor parameter, and its `IsSuperAdmin` checks them when they are given; without them there is still no super admin unless it is overridden, so a custom permission service keeps working as before. Switches, including Bootstrap's `form-switch`, are 2.25em by 1.25em instead of 2em by 1em, so they no longer look thin next to text and buttons, have a pointer cursor, and take their size from the optional `--s-switch-width` and `--s-switch-height` tokens, in the new `switch.css` of Serenity.Extensions that the Serene and StartSharp themes share.

### Bugfixes
- `TwoFactorManager.IsActiveFor` returned true for a user without an active two-factor method and false for one with it.
- Files dropped on or pasted into a read-only upload editor were uploaded and set as its value, as the drop zone of the `Uploader` did not check whether its file input was disabled; they are ignored now, and the editors also ignore a file that finishes uploading after they became read-only. The drop zone also kept its `drop-valid` or `drop-invalid` class after a drop, as no dragleave follows it.

## 10.8.1 (2026-11-26)

### Bugfixes
- The CSS bundle builder could hang forever, keeping a CPU core busy in the meantime, on a stylesheet that starts with a comment and has comments that directly follow another comment, e.g. a 57 KB one with 28 such pairs, so every request for a bundle that includes it waited until the request was abandoned or the application was restarted: the leading comment/whitespace run of the `@import` pattern of `CssBundleBuilder` could be matched in exponentially many ways, doubling with every such pair, and its comment atom is unambiguous now, so matching is linear in the file size. The pattern also has a timeout of 5 seconds as a safety net, after which the file is included with its `@import` statements as is and a warning is logged, and so do the patterns that rewrite relative urls and remove source mapping comments, which could take quadratic time for unusual content. For earlier versions, setting `CssBundling:ProcessImports` to `false` avoids the pattern.
- Sergen and the source generators could hang on a name of ~30 or more valid identifier characters followed by an invalid one, e.g. a long local text key segment or module name with a space, dash or slash in it, as the identifier pattern of `CSharpSyntaxRules` repeated its part characters twice and took exponential time; it is linear now.
- `GlobFilter` took exponential time for a pattern with `**/` that is not one of its fast paths, e.g. `**/x.css`, and a path of many folders that does not match, e.g. 16 seconds for 30 folders; `**/` is converted to an equivalent pattern that is not ambiguous.
- The TypeScript scanner of the code generator never recognized `@ts-ignore` and `@ts-expect-error` comment directives, as the multi-line pattern was escaped twice and the single-line one expected a trailing slash, and the multi-line pattern took exponential time for a comment line starting with many backslashes.
- The in-memory list source adapter of Pro.Extensions matched the `LIKE` pattern of a list request with a regular expression that it built from the pattern, which took seconds for a pattern with several `%`, e.g. `%a%a%a%b` against a text of 1000 characters, as the ways the text can be split among the `%` signs grow with its length to the power of their number, so such a request could stall the services that the adapter serves; literals and wildcards are matched with a two-pointer matcher now, which needs at most a pass over the text for each `%` and never backtracks, and an escaped `%` or `_` is still a literal and the comparison is still case-insensitive unless `IsLikeCaseSensitive` says otherwise (StartSharp).
- `ExceptionLog` of Pro.Extensions masked the form fields of a logged error, e.g. the `Password` of a login, at the value of the field instead of at its key, so the secret stayed in the form data of the error and the `***` was stored under the value; it replaces the value of the key now (StartSharp).
